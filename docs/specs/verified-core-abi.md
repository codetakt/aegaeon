# Verified Core ABI Snapshot (v1)

Last updated: 2026-07-07

Status: current implementation baseline

Owner: Product / Engineering

Audience: implementers, reviewers

> **Status note (2026-03-09):** This ABI snapshot documents a host/runtime surface, not the current strong-constraint claim boundary. Mentions of `RS256` / `ES256` here describe compatibility targets unless and until a separate boundary-closure decision promotes them. Current Verified Core WASM claims verification is functional for `EdDSA`; `iss` / `aud` checks and DPoP `ath` binding are now handled inside the C exports layer rather than as dedicated host callbacks.

Snapshot update date: 2026-03-09

The authoritative record of imports/exports and data layouts exposed by
Verified Core's WebAssembly module is stored in
`generated/lowstar/verified-core/verified_core.abi.json`.
This JSON is based on a manually maintained template
and generated by `scripts/sdk/generate_verified_core_abi.js`.

```bash
node scripts/sdk/generate_verified_core_abi.js
```

The script simply adds `generatedAt` to the template and writes the JSON.
It does not depend on the KaRaMeL header structure, allowing the WASM/host
boundary specification to be fixed as intended.

## Key Conventions

- **Byte sequences**: The host manages `bytes_handle (u32)`. Handles must remain valid throughout the call and may be released afterward. Use `FStar_Bytes_read` for bulk copying.
- **Time**: `u64` (Unix seconds). Pass values as `BigInt` from JavaScript.
- **Integers**: Lengths and indices are `u32`. Error codes are `VerifiedCoreStatusCode (u32)`.
- **ES256 signature format**: The ABI uses JOSE/P1363 (64 bytes of `r || s`) as the canonical format. If a future compat/runtime adapter accepts `ES256`, handle DER ↔︎ P1363 conversion outside the verified WASM boundary.
- **Replay Store**: `ReplayStore_check_and_store` corresponds to Redis `SET key 1 NX PX ttl`; treat `UNAVAILABLE` as fail-closed.

## Claims-Based Verification Path

In addition to the existing compact input format (`*_verify_v1`), a **claims-based verification path** (`*_verify_claims_v1`) is provided.
The claims path performs Base64/JSON parsing on the host and passes only previously parsed byte sequences to Verified Core.

### Benefits

- **Smaller TCB**: No Base64/JSON parser needs to run inside Verified Core, reducing the code to be verified.
- **Flexibility**: Hosts can implement their own JWS parsers and caching strategies.
- **Compatibility**: Uses the same output structure as the existing compact path.

## Import/Export Overview

### Imports
- `VerifiedCore_Api_Claims_Runtime_host_replay_store_check_and_store` – Calls an external store such as Redis and performs replay checking and TTL registration together.
- `vc_host_register_bytes` / `vc_host_release_handle` – Promote raw byte sequences in WASM linear memory to host-managed handles and release them.
- `Host_parse_dpop_compact` / `Host_parse_jwt_compact` – Parse compact JWS inputs in advance and return claims / signing input / signature / key handles.
- `Host_handle_data_ptr / Host_handle_data_len` – Resolve a bytes handle to `(ptr, len)` in WASM linear memory.

### Reference adapter replay-store results

The Node and Web reference adapters require the synchronous
`replayStore.checkAndStore(namespace, keyHash, ttlMs)` callback to return a
boolean: `false` means a fresh registration and `true` means replay. Every
other return value maps to the unavailable result, including `undefined`,
`null`, numbers, strings and promises. Exceptions propagate to the caller.
Custom stores must return explicit booleans; a missing return value cannot
admit a request as fresh.

### Reference adapter DPoP time values

The Node and Web reference adapters encode DPoP time values as integer seconds.
`iatSeconds` and `nowUnixTimeSeconds` must be non-negative integer `number` or
`bigint` values that fit `u64`; policy values `maxAgeSeconds` and
`maxFutureSkewSeconds` must be integer `number` values in the `u32` range.
Invalid values throw before the WASM verification call instead of wrapping or
being coerced. Low-level field writers retain their existing zero defaults for
optional fields; higher-level API defaults and required fields are unchanged.
Use `bigint` when a JavaScript `number` cannot represent the intended second
exactly; the adapter cannot recover precision lost before the API call.

For compact DPoP proofs, the root `iat` JSON number is converted from its original
number token, preserving values such as `9007199254740993`. Decimal or exponent
notation is accepted when its exact value is an integer in the `u64` range;
negative, fractional and out-of-range values are rejected without rounding.
JSON parsing retains its existing last-member behavior for duplicate names.
The signed JWS bytes are preserved. This integer-seconds ABI does not add support
for fractional NumericDate values (RFC 7519 §2; DPoP `iat`: RFC 9449 §4.2).

### Claims Path Imports
The **replay store** is the only remaining **functional verification dependency** in the claims-based verification path.
- `VerifiedCore_Api_Claims_Runtime_host_replay_store_check_and_store` – Replay detection

`iss` / `aud` matching, `ath` binding, SHA-256, Ed25519 signature verification, and the Low* compat/math shim are handled by WASM + the C exports layer in the current verified WASM path, without host callbacks.

Global flag constants:
- `VerifiedCore_Api_Claims_Runtime_dpop_flag_require_ath` (= 1)
- `VerifiedCore_Api_Claims_Runtime_dpop_flag_require_jti` (= 2)
- `VerifiedCore_Api_Claims_Runtime_jwt_flag_require_exp` (= 1)
- `VerifiedCore_Api_Claims_Runtime_jwt_flag_require_iat` (= 2)
- `VerifiedCore_Api_Claims_Runtime_jwt_flag_require_nbf` (= 4)

### Exports
- `VerifiedCore_dpop_verify_v1` – DPoP verification (compact input via the host parser). Returns EdDSA signature verification results and replay semantics in the current verified WASM path.
- `VerifiedCore_jwt_verify_v1` – JWT verification (compact input via the host parser). Returns EdDSA signature verification results and optional issuer/audience checks in the current verified WASM path.
- `VerifiedCore_dpop_verify_claims_v1` – **Claims path**: DPoP verification with previously parsed inputs.
- `VerifiedCore_jwt_verify_claims_v1` – **Claims path**: JWT verification with previously parsed inputs.

## Operational Policy

- The JSON is the **sole authoritative record**. Keep documentation to supplementary explanations (background and caveats); when the JSON needs to change, update the generation script and regenerate it.
- Breaking ABI changes (field position changes, enum value changes, etc.) require a major bump to `abiVersion`.
- When adding imports/exports in Verified Core or the SDK, update this template first, then rerun the script and check the diff.

## Host Implementer Checklist

1. Implement `vc_host_register_bytes` / `vc_host_release_handle` and ensure handles remain live throughout calls.
2. Implement `Host_parse_*` and `Host_handle_data_*` to fail closed; do not treat invalid handles / parse errors as success.
3. Map `ReplayStore_check_and_store` to SET NX PX in Redis or equivalent, and return `UNAVAILABLE` to the caller as a fail-closed result.
4. Respect `allowedAlgorithmsBitmask` in `dpopVerify` / `jwtVerify` implementations; do not use disabled algorithms.
5. Validate the generated output (`verified_core.abi.json`) in CI and keep it consistent with the SDK/runtimes.
