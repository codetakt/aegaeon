# Formal Verification Scope And Proof Quality

Last updated: 2026-07-27

Status: current implementation baseline

Owner: Verification

Audience: verification reviewers, maintainers

This document is part of the split formal verification assurance case.

## 1. Verification Scope

Aegaeon employs four complementary verification tools, each targeting a
different property class. Together they cover specification-level correctness,
protocol security, memory safety, and parser correctness.

### 1.1 F\* — Functional Correctness and Security Specifications

| Metric | Value |
|---|---|
| Verified modules | 155 unique (Pass 1: 4, Pass 1b: 10, Pass 2: 150; some modules appear in multiple passes; see `scripts/flake/verify_fstar.sh`) |
| `admit()` calls | **0** |
| `assume val` declarations | 12 (across 8 files; 6 crypto, 2 HACL\* linkage, 1 EverParse linkage, 2 OIDC hash runtime linkage, 1 WASM host) |
| Verification script | `scripts/flake/verify_fstar.sh` |
| CI gate | `nix build .#verify-fstar` |

**What is verified:**

- **JOSE stack** — JWS creation/verification, JWE encryption/decryption, JWT
  claim validation, JWK structure and thumbprint computation, algorithm policy
  enforcement, header parsing (pure `Tot` parser on `FStar.Seq`), SD-JWT
  selective disclosure with digest collision resistance.
- **OAuth 2.0/2.1 token flows** — Authorization code issuance and redemption,
  access token storage and lookup, refresh token rotation, PKCE challenge/verify
  (S256 modeled with `irreducible`), token binding, bearer token validation.
- **DPoP (RFC 9449)** — Header validation, claim structure, signature
  verification, `ath` hash binding, `htm`/`htu` validation, replay detection,
  nonce generation and rotation.
- **PAR (RFC 9126)** — Request object validation, pushed authorization request
  binding and lifetime, client authentication, response structure, redirect
  integrity.
- **DCR/DCR Management (RFC 7591/7592)** — Registration request validation,
  client lifecycle (create/update/soft-delete), key rotation, policy profile
  enforcement.
- **Federation (OIDC Federation)** — Entity configuration, subordinate
  statements, trust chain resolution with policy algebra (merge, order,
  restrictiveness), trust anchor registry, trust mark verification, upstream
  refresh rotation, OIDC RP state machine (types, transitions, properties).
- **Token types** — JWT access tokens (RFC 9068) with `cnf` binding, bearer
  policy, token introspection (RFC 7662), JWT introspection (RFC 9701).
- **Device Authorization (RFC 8628)** — Device code lifecycle, single-use
  enforcement, polling state machine.
- **Step-up authentication** — ACR enforcement, challenge issuance.
- **Resource indicators** — Well-formedness, HTTPS validation, protected
  resource metadata.
- **Hash computation** — OIDC hash (`at_hash`, `c_hash`) computation and
  verification, collision resistance (honest `assume val` on HACL\* SHA-256).
- **Low\* / LowStar** — Buffer-based JSON parsing pipeline, TLV encoding, UTF-8
  handling, memory allocation contracts.
- **WASM verified core** — Host callback contract for the portable
  verification module (replay store only). SHA-256 and Ed25519 verification
  are internalized via HACL\* inside the WASM artifact. When the server links
  the native C output directly, this boundary applies only to the distributed
  WASM artifact.

**What the 0 `admit()` guarantee means:** Every proof obligation generated by
the F\* type-checker is discharged by Z3. No proof goal is skipped. The 12
`assume val` declarations (6 crypto hardness, 2 HACL\* linkage,
1 EverParse linkage, 2 OIDC hash runtime linkage, 1 WASM host) are the *only*
module-level unproved trust assumptions — each is documented in the
[Assumption Register](../assumptions/current-register.md). Zero inline `assume`
statements remain.

network, can intercept/modify/replay messages, and can compromise long-term
secrets via explicit corruption rules. Cryptographic primitives are modeled as

### 1.3 Kani — Bounded Model Checking for Rust

| Metric | Value |
|---|---|
| Proof harnesses | 139 |
| Harness files | 15 |
| CI gate | `nix build .#verify-kani` |

Kani uses the CBMC model checker to exhaustively explore all execution paths
within bounded inputs. It verifies absence of:

- Integer overflow/underflow
- Out-of-bounds array access
- Undefined behavior in arithmetic operations
- Assertion violations in Rust code

**Coverage areas:** JOSE header parsing, DPoP JTI handling, authorization code
verification and snapshot invariants, token store operations, JWKS input guards
and circuit breaker, federation entity configuration, subordinate statement
parsing, device authorization flows, JWT introspection response handling.

**Limitation:** HashMap-heavy harnesses can trigger CBMC internal compiler errors
(ICEs) or state-space explosion. These are documented as known limitations and
worked around with bounded array models.

### 1.4 EverParse — Parser/Serializer Verification

| Metric | Value |
|---|---|
| `.3d` schema definitions | 7 |
| F\*-verified in CI | 7 (`JoseHeader`, `DCR`, `IdTokenSchema`, `DpopSchema`, `DcrRegistration`, `LogoutTokenSchema`, `RequestObjectSchema`) |
| Generated but not F\*-verified | 0 |
| Rust FFI wrappers available | 5 (`JoseHeader`, `DCR`, `Dpop`, `IdTokenSchema`, `RequestObjectSchema`) |
| Runtime-invoked in server | 4 (`JoseHeader`, `DCR`, `Dpop`, `RequestObjectSchema` opt-in) |

EverParse generates memory-safe C parsers from `.3d` schema definitions. These
validate TLV-encoded binary payloads at the Rust-to-C FFI boundary, providing
defense-in-depth for protocol messages that have already been parsed at the
Rust/serde level.

**What EverParse guarantees for verified schemas:**
- Generated parsers are memory-safe (no buffer overruns)
- Parsers accept exactly the language defined by the `.3d` grammar
- Parser/serializer roundtrip: `serialize(parse(x)) == x` for valid inputs

### 1.5 Assumption-Qualified Verification

All verification results in this document are **conditional** on the 12
`assume val` declarations documented in the
[Assumption Register](../assumptions/current-register.md). These assumptions form an explicit,
auditable boundary between verified specifications and unverified runtime
components. Every `assume val` is categorized by type (crypto / HACL\* linkage /
EverParse linkage / OIDC hash runtime linkage / WASM host) and assigned a risk
level.

**Aegaeon is formally verified modulo the assumptions in the Assumption
Register.** Specifically: given that the 12 assumed function contracts are
faithfully implemented by their runtime counterparts, all F\* proof obligations
(0 `admit()`) and all Tamarin lemmas (248/248) hold. A violation of any assumed
contract could invalidate proofs that depend on it.
The claim additionally presupposes the runtime contracts RC-1 through RC-7
enumerated in the
[Runtime Contract Register](../assumptions/runtime-contract-register.md).

The 12 assumptions break down as follows:
- **6 cryptographic trust boundaries** (permanent) — honest computational
  hardness assumptions: SHA-256 collision resistance (4, backed by HACL\* specs),
  Ed25519 EUF-CMA unforgeability (2, backed by HACL\* specs). Phase A
  replaced identity/false/constant crypto models with genuine spec implementations,
  converted tautological proofs into honest assumptions, and eliminated
  DRBG hmac\_sha256 via Bridge delegation to HACL\*.
- **2 HACL\* linkage assumptions** (permanent) — verified foreign code
  boundaries (`hacl_sha256`, `hacl_ed25519_verify`) used inside the WASM
  artifact. These are not host callbacks.
- **1 EverParse linkage assumption** (permanent) — a narrow bridge to the
  generated JOSE header entry validator.
- **2 OIDC hash runtime linkage assumptions** (permanent) — local C bridge
  contracts for bounded buffer-prefix extraction and HACL\*/EverCrypt SHA-2
  dispatch in the OIDC hash runtime path.
- **0 FFI / C runtime stubs** — all 9 original FFI stubs (8 + 1 bridge) have
  been eliminated via concrete Low\* implementations using `LowStar.Buffer`
  separation logic. Category B = 0.
- **1 WASM host import** (permanent) — callback contract for the portable
  verification module (`host_replay_store_check_and_store`).
- **0 encoding model boundaries** — all 4 Base64url/Base64 roundtrip and
  injectivity `assume val` properties have been replaced with concrete
  implementations and proved lemmas. Category E = 0.

**Plain-language summary for external communication:** Aegaeon's core protocol
logic — OAuth 2.0/2.1 authorization flows, token lifecycle, DPoP proof
validation, PKCE, federation trust chains, and SD-JWT selective disclosure — has
formal, assumption-qualified evidence in the documented verification models.
The 12 remaining assumptions are: 6 standard cryptographic hardness properties
(SHA-256 collision resistance, Ed25519/HMAC unforgeability), 2 HACL\* linkage
assumptions, 1 EverParse linkage assumption, 2 OIDC hash runtime linkage
assumptions, and 1 WASM host import contract. All 12 are individually
documented, risk-assessed, and auditable in the project's Assumption Register.

### 1.6 Proof Quality Classification

Each proof block in the compliance matrix is classified along two dimensions:

**Quality** — determined by `proof[].type`:
- **Formal**: `fstar`, `tamarin`, `kani`, `everparse`, `lowstar`, `hacl` — machine-checked mathematical proof or bounded exhaustive analysis
- **Empirical**: `dudect` — statistical testing under documented parameters; not a mathematical proof
- **Unknown**: `policy`, `plan`, `code_review`, `property_test`, `rust_test`, `unit_test`, etc. — auxiliary evidence that does not constitute a formal or empirical proof; recorded for traceability but **not sufficient** to qualify an entry as `verified`

**Strength** — determined by the evidence fields present:
- **Lemma**: `lemma` or `harness` field present (or `spec` for EverParse) — references an exact, greppable proof artifact
- **Refinement**: `refinement` field present — references a type-system refinement constraint
- **Semantic**: all other evidence (e.g., `invariant`) — describes a verified property without an exact identifier

**Current status:** All 182 verified entries have at least one formal proof
reference, and all 292 formal proof blocks are **grounded in an on-disk
artifact** (file plus, where named, a definition or lemma that the CI gate greps
for). No entries rely solely on empirical evidence. The proof-block inventory is
341 total blocks: 292 formal, 0 empirical, and 49 auxiliary/unknown blocks. The
proof strength breakdown is: lemma 160, refinement 2, semantic 179 (proof-block
level; entries may have multiple blocks at different strengths). Grounding is
enforced fail-closed by `scripts/validation/verify_verified_reqs.py --strict`
(`.#verified-reqs`); an ungrounded sibling block fails the row rather than being
masked by another grounded block.

#### Refinement Trace

`trace` entries in `spec/compliance-matrix.yaml` record the implementation
connection from a formal artifact to runtime evidence. The validator accepts
four trace kinds:

- `oracle`: an F* specification function and Rust implementation symbol are
  compared by a differential test; `test` is required.
- `structural`: a type, parser, or generated artifact correspondence is
  grounded by references; `test` is optional.
- `guard`: the specification property is enforced as an HTTP-boundary rejection
  guard and fixed by an integration test; `test` is required.
- `exempt`: no direct function correspondence is meaningful; `note` must give
  the one-sentence reason.

**Current coverage (2026-07-29):**
`scripts/validation/verify_verified_reqs.py --strict` reports
`Refinement Trace: 161/161 MUST-level verified (oracle=11, structural=2,
guard=109, exempt=39)`. Every `MUST` / `MUST NOT` verified entry carries a
validated trace; the 39 `exempt` entries each name the protocol-level
(Tamarin), harness-level (Kani/EverParse/Low\*), or model-scope reason why no
F\* function-level counterpart exists.

**Level 2 condition (met, gate-enforced):** all `MUST` / `MUST NOT` verified
entries must carry a valid trace. The gate
`python3 scripts/validation/verify_verified_reqs.py --strict --require-trace-must`
passes and is enforced in CI via `.#verified-reqs`
(`scripts/flake/verify_reqs.sh`), so a future MUST-level `verified` entry
without a trace fails the merge gate.

Trace kinds carry different assurance weights: an `oracle` trace pins runtime
behaviour to the F\* function by differential test; `structural` pins a
type/parser correspondence; `guard` pins the property to a production decision
symbol fixed by an existing test but without a differential oracle; `exempt`
records that the connection claim does not apply at function granularity. The
Level 2 claim is therefore a connection-coverage claim, not a proof that every
traced Rust function refines its F\* counterpart.

**Policy:** An entry with only `dudect` evidence (empirical quality, no formal
supplement) should use `status: implemented`, not `status: verified`. The
`verified` status requires at least one formal proof reference. If a dudect
check is supplemented by an F\* or Tamarin proof, the entry qualifies as
`verified` and the dudect block provides additional empirical assurance.

See [claim-index.md](../claim-index.md) for the current quality and strength
breakdown.
